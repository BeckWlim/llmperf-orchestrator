# LLMPerf Task Compiler Architecture

## Purpose

The Task Compiler turns a readable, finite experiment workflow into a static logical DAG.
It does not schedule work, wait for time to pass, call Providers, or persist authoritative
state. Its output is a deterministic intermediate table that can be inspected before any
runtime UUID or database record exists.

The primary design goals are:

1. make the YAML hierarchy match the task primitive hierarchy;
2. represent every primitive as an immutable `BaseNode` subclass;
3. keep external syntax validation, semantic compilation, and persistence assembly as
   separate phases;
4. make expansion deterministic and testable without UUID assertions;
5. add generic composition primitives without changing Planner or Scheduler behavior;
6. reject unbounded, ambiguous, or excessively large graphs before persistence.

## Ownership boundary

Task-specific Pydantic models live in `task_compiler.py`, not the general Backend
`models.py`. This makes the compiler the owner of both its external AST and its internal
node model.

```text
Campaign YAML
    │
    ▼
TaskDefinitionCreate / TaskRecipe       Pydantic syntax boundary
    │
    ▼
TaskGraph(BaseNode...)                  immutable semantic graph
    │ expand matrix × trials
    ▼
CompilationTable                        stable, UUID-free compiler IR
    │ assemble runtime identities
    ▼
TaskInstanceAssembly / TaskNodeAssembly serialized Runner + UUID dependencies
    │
    ▼
PostgreSQL Task Instance + Dispatch rows
    │
    ▼
Planner -> Runner -> Scheduler -> Worker
```

`TaskDefinitionCreate` is generic over its owning Runner input. `models.py` binds that
compiler-owned AST to `BenchmarkRunnerSpec` for the Campaign request model. It does not
interpret task nodes, resolve dimensions, estimate spans, or expand the graph.

## Pydantic's role

Pydantic defines the strict external compiler AST:

- `TaskDefinitionCreate` validates a submitted definition and its Runner;
- `TaskRecipe` is the Runner-independent compiler input;
- `TaskNodeSpec` enforces exactly one primitive per YAML mapping;
- `InvokeConfig`, `RepeatConfig`, `ParallelConfig`, and `SequenceConfig` validate primitive
  fields;
- `DimensionReference` normalizes `$dimension_name` expressions.

Pydantic does not build dependency lists or assign runtime identities. Semantic validation
delegates to `TaskCompiler.validate_recipe()`, so expansion limits and topology rules use
the same node implementation as real compilation.

The former `sequence`/`kind` syntax is normalized at this input boundary into `workflow`
AST nodes. No legacy branch remains in graph expansion, estimation, assembly, persistence,
Planner, or Scheduler.

## Readable task DSL

`workflow` is an implicit top-level sequence. Each item is a one-key mapping whose key is
the primitive being composed:

```yaml
task_definitions:
  - name: retention-surface
    instances:
      matrix:
        delay_seconds: [60, 300, 900]
      trials: 5
      seed: 20260820
    payloads:
      replay: {seed_namespace: replay}
      cold: {seed_namespace: cold-control}
    workflow:
      - invoke:
          name: prime
          payload: replay
      - parallel:
          name: observation
          after_seconds: $delay_seconds
          branches:
            - invoke:
                name: warm
                payload: replay
            - invoke:
                name: cold
                role: cold_control
                payload: cold
    runner: {}
```

The primitive name is visible before its fields. Structural nesting in YAML is therefore
the same nesting used by the compiler. `role` defaults to `name` and only needs to be
written when analysis terminology differs from topology terminology.

`instances` is the single expansion boundary around the graph: it owns `matrix`, `trials`,
and the deterministic `seed`. These fields are deliberately not accepted beside
`workflow`, because they produce independent graph instances rather than graph nodes. The
YAML contains exactly one `instances` object, not a list; the plural name denotes the set
of TaskInstances generated by its Cartesian matrix and trial count.

### Primitive semantics

| Primitive | Meaning | Incoming frontier | Outgoing frontier |
|---|---|---|---|
| `invoke` | One atomic Provider request | All declared predecessors | The emitted node |
| `repeat` | Bounded serial expansion of one nested node | Previous step | Last iteration |
| `parallel` | Concurrent expansion of nested branches | Shared by every branch | Union of branch frontiers |
| `sequence` | Nested ordered composition | First nested step | Last nested step |

The top-level `workflow` behaves like `sequence` without adding a path segment.

## Node hierarchy

`BaseNode` defines the common compiler contract:

```text
BaseNode
├── InvokeNode
├── RepeatNode
├── ParallelNode
└── SequenceNode
```

Every subclass is immutable and implements:

- `from_config()` to construct semantic state from its validated Pydantic config;
- `expand()` to append logical rows and return its outgoing dependency frontier.

`NODE_TYPES` is the primitive registry. Adding a generic primitive requires a config model,
a `BaseNode` subclass, and one registry entry. The main compiler loop does not contain a
growing `if kind == ...` chain.

Nested paths produce stable logical node IDs:

```text
prime
warmups.1.warmup
warmups.2.warmup
observation.probe
observation.cold
```

These names are compiler identities and audit evidence. They are not database UUIDs.

## Compilation table

The compiler caches expansion in a normalized in-memory table before serialization.

`CompiledInstanceRow` contains:

- stable `instance_key`;
- resolved matrix dimensions;
- zero-based trial index.

`CompiledNodeRow` contains:

- owning `instance_key`;
- stable logical `node_id`;
- logical dependency node IDs;
- `after_seconds`;
- role and payload ID;
- deterministic payload seed.

`CompilationTable` stores both row sets and indexes nodes by `instance_key`. Estimation,
topology inspection, planned-span calculation, and assembly all consume this same IR. An
instance remains represented even when its workflow expands to zero invokes.

The table deliberately contains no timestamps, database records, Runner IDs, Dispatch IDs,
or mutable execution state.

## Runtime assembly

`TaskAssembler` is the only phase that assigns runtime UUIDs. For each instance it:

1. allocates one Task Instance ID;
2. allocates one Dispatch ID for every logical node;
3. maps logical dependency node IDs to Dispatch IDs;
4. injects the instance/node/payload context into a single-request Runner template;
5. validates the compiled benchmark configuration;
6. returns immutable assembly records for persistence.

This boundary keeps UUID generation out of graph semantics. Tests can compile and compare a
stable table, while persistence receives fully assembled records with no topology decisions
left to make.

## Determinism and safety invariants

- Matrix dimensions are expanded in sorted-name order.
- Payload seeds derive from the global seed, sorted coordinates, trial index, and payload
  seed namespace.
- Reusing a payload ID within an instance yields the same seed.
- Node paths are unique within one instance and limited to 120 characters.
- Every expression references a declared dimension.
- Repeat counts are resolved and bounded before persistence.
- Graph nesting, instances, and nodes per instance have explicit hard limits.
- Longest dependency-path delay cannot exceed six hours.
- All compiled Runner nodes force one request at concurrency one.
- A parallel join depends on every outgoing branch frontier.
- UUID assignment cannot change graph shape, node order, seeds, or planned delays.

## Extension procedure

To add a new provider-neutral composition primitive:

1. define its strict Pydantic config in `task_compiler.py`;
2. add it to `TaskNodeSpec` as another one-key primitive;
3. implement an immutable `BaseNode` subclass;
4. register the primitive in `NODE_TYPES`;
5. define its frontier and delay behavior in unit tests;
6. document its bounded YAML form and safety limits.

Do not add experiment names, cache-specific roles, Provider conditions, Planner branches,
or Scheduler branches. A primitive is appropriate only when it has generic static-DAG
semantics and can be fully expanded during admission.

## Verification strategy

Compiler tests operate at four independent levels:

1. Pydantic AST tests reject malformed primitives and unresolved references;
2. node hierarchy tests verify recursive composition and frontier behavior;
3. compilation-table tests verify stable paths, dependencies, delays, and payload seeds;
4. assembly tests verify UUID mapping and compiled Runner validation.

API, safety-gate, persistence, and Planner tests then verify integration boundaries. The
Planner is expected to remain unaware of compiler primitive classes.
